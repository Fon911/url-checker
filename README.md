# URL Checker

Сервис асинхронной проверки списка URL.
Бэкенд — NestJS (TypeScript), фронтенд — React + Vite + Zustand, хранение в памяти.

## Запуск через Docker

```
docker compose up --build
```

Фронтенд: http://localhost:3000, API: http://localhost:4000/api

## Запуск без Docker

Нужен Node.js 22+.

Бэкенд (порт 4000):

```
cd backend
npm install
npm run start:dev
```

Фронтенд (порт 5173, запросы к /api проксируются на бэкенд):

```
cd frontend
npm install
npm run dev
```

## API

- `POST /api/jobs` — создать задание. Тело: `{ "urls": ["https://example.com"] }`, ответ: `{ "jobId": "..." }`
- `GET /api/jobs` — список заданий: статус, количество URL, статистика успешно / с ошибкой
- `GET /api/jobs/:id` — детали задания: статус каждого URL, HTTP-код, ошибка, время обработки
- `DELETE /api/jobs/:id` — отменить задание, не начатые URL помечаются как cancelled

## Как устроена проверка

Задание обрабатывается в фоне: на каждый URL выполняется HEAD-запрос,
одновременно не больше 5 запросов на задание, несколько заданий могут идти
параллельно. Перед сохранением результата — случайная задержка 0–10 секунд.
При отмене уже запущенные проверки довыполняются, их результат сохраняется.

Задание считается `failed`, если ни один URL не проверился успешно.
На одно задание принимается до 1000 URL.

## Что можно улучшить

Осознанные упрощения в рамках тестового задания:

- Задания хранятся в памяти (`Map`) и не удаляются — для прода нужен
  persistent-store и очистка старых заданий по TTL.
- HEAD-запрос идёт на любой присланный URL без фильтрации хостов. Это SSRF-риск
  (можно постучаться на localhost или в приватную сеть); для реального сервиса
  нужен блок-лист приватных диапазонов.
- Статус активного задания опрашивается коротким polling'ом. При росте нагрузки
  логичнее перейти на SSE или WebSocket.
- `npm audit` в бэкенде показывает high в `multer` — это транзитивная зависимость
  `@nestjs/platform-express`, в коде задания загрузка файлов не используется.
